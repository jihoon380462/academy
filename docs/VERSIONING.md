# 버전 관리와 공개 반영 기록

이 저장소의 코드·학습 콘텐츠·운영 문서는 Git 이력과 변경 기록으로 관리한다. 새 대화에서도 이 규칙을 이어간다. 사용자의 작업 범위와 이미 주어진 권한을 우선하며, 이 문서는 별도의 승인 절차를 추가하지 않는다. PR만 요청받은 작업은 PR 생성에서 마치고 병합·태그·배포를 임의로 진행하지 않는다.

## 무엇을 어디에 기록하는가

| 파일·표식 | 역할 |
| --- | --- |
| 루트 `VERSION` | 현재 소스가 목표로 하는 사이트 버전 한 줄. 현재 공개 버전을 보장하는 값은 아님 |
| `CHANGELOG.md` | 미공개 변경은 `Unreleased`, 릴리스한 변경은 버전·날짜별로 정리 |
| `verification.md` | 검증한 소스 SHA, 환경·결과, Pages 실행 링크·배포 SHA, 실제 사이트 확인 여부 |
| Git 커밋·PR | 변경 범위와 이유, 검증 결과를 추적하고 복구하는 단위 |
| `vX.Y.Z` 태그·GitHub Release | 검증을 마친 릴리스의 고정 표식. 해당 배포의 정확한 소스 커밋을 가리킴 |

`구현 완료`, `PR 병합`, `Pages 배포 성공`, `실제 공개 화면 확인`은 서로 다른 상태다. 해당 단계의 증거가 있을 때만 완료로 기록한다. 저장소에 변경이 있다고 공개 사이트도 바뀌었다고 보고하지 않는다.

## 버전 번호

`MAJOR.MINOR.PATCH` 형식을 쓴다. 최초 목표는 `0.1.0`이며 아직 릴리스했다는 뜻은 아니다. 과거 작업에 번호나 배포 날짜를 소급해 만들지 않는다. 아래 규칙은 0.x에서도 적용한다.

| 변경 | 올릴 자리 | 예시 |
| --- | --- | --- |
| 기존 URL·저장 형식 등에 비호환 변경 | MAJOR | `0.3.2` → `1.0.0` |
| 기존 사용 방식을 유지하는 기능·챕터·레슨 추가 | MINOR | `0.3.2` → `0.4.0` |
| 화면 오류, 콘텐츠·정답 오류, 오탈자, 기존 기능 수정 | PATCH | `0.3.2` → `0.3.3` |
| 운영 문서·검증 기록만 수정 | 번호 유지 | `AGENTS.md`나 배포 실패 기록 수정 |

큰 자리를 올리면 아래 자리는 0으로 만든다. 학습자가 읽는 본문·문제 변경은 콘텐츠 변경이며 운영 문서 전용 변경으로 취급하지 않는다. 리팩터링·빌드 수정도 공개 파일에 영향을 주면 PATCH 대상으로 기록한다.

버전은 커밋마다 올리지 않고 공개할 변경 묶음마다 정한다. 이미 미공개 목표 버전이 있으면 변경을 같은 `Unreleased`에 모으고, 더 큰 변경 종류가 추가될 때 목표 번호를 조정한다. 첫 목표 `0.1.0`도 이 원칙을 따른다. 동시에 진행한 PR은 병합 전 최신 `main`의 번호·변경 기록을 다시 확인해 중복 번호와 누락을 정리한다.

번호를 올리는 것만으로 기존 링크를 끊거나 학습 기록을 지워도 되는 것은 아니다. 비호환 변경에는 영향과 호환·이전 방법을 함께 설계하고 요청된 작업 범위 안에서 처리한다.

## 매 작업에서 지킬 순서

1. 최신 `main`과 작업 트리를 확인하고 `VERSION`, `CHANGELOG.md`, 최근 `verification.md`를 읽는다. 다른 작업자의 변경을 덮어쓰지 않는다.
2. 목적이 드러나는 작업 브랜치에서 변경한다. 커밋은 의미 있는 단위로 남기고 메시지에 변경 목적을 적는다. 이미 공유한 이력이나 릴리스 태그를 강제로 바꾸지 않는다.
3. 코드·콘텐츠 변경의 종류에 맞춰 목표 버전과 `Unreleased`를 갱신한다. 운영 문서만 바꾸면 목표 번호를 유지하며 문서 변경을 기록한다. 단순 검증 결과 추가는 `verification.md`에 기록한다.
4. 변경에 필요한 검증만 수행하고 실제 수행 결과를 남긴다. 파이썬 콘텐츠를 바꾸면 `python3 build-python.py --check-code`와 생성물 갱신을 포함한다. 화면 변경은 PC·모바일과 관련 테마·기록 보존을 확인한다. 문서만 바꾼 경우에는 링크와 내용의 일관성을 확인하며 앱 테스트를 수행한 것처럼 쓰지 않는다.
5. PR에 문제와 결과, 변경 범위, 목표 버전 또는 번호 유지 이유, 검증 결과를 적는다. 병합·배포·릴리스는 사용자가 지시한 범위와 기존 권한에 맞게 진행한다.

## 캐시 번호와 학습 기록은 별개다

- 사이트 버전은 `VERSION`, 정적 자산의 캐시 식별자는 `index.html` 등의 `?v=...`, 저장 형식은 `localStorage` 키로 각각 관리한다. 서로 자동으로 맞추지 않는다.
- 배포할 CSS·JavaScript 내용이 달라졌으면 해당 파일을 사용하는 운영 진입점과 관련 미리보기의 참조를 확인해 캐시 식별자도 새 값으로 바꾼다. 새 값은 목표 버전과 고유 변경 번호를 조합할 수 있다(예: `0.1.1-1`). 같은 목표 버전 안에서 파일을 다시 수정하면 식별자도 갱신한다. 변경하지 않은 자산을 일괄 갱신하지 않는다.
- 현재 날짜 기반 `?v=` 값은 다음에 해당 자산이 바뀔 때까지 유지해도 된다. 버전 관리 도입이나 문서 변경만을 이유로 앱 파일을 수정하지 않는다.
- `understand-math-grade1-v1`, 파이썬 챕터별 `academy-python-ch01-v1`~`academy-python-ch09-v1`, `academy-theme-v1`은 사이트 버전을 올려도 유지한다. 새 챕터에는 독립 키를 쓰고 기존 기록을 보존한다. 저장 구조 변경이 필요하면 이전 로직과 기존 데이터 보존을 검증한다.

## 배포·릴리스 확인

현재 Pages는 `main` / `/ (root)`의 소스를 배포한다. 설정 변경은 버전 관리 도입에 포함하지 않는다.

1. 배포 대상 커밋 SHA와 해당 Pages 실행 링크를 기록한다. PR이 병합되었어도 배포 결과는 따로 확인한다.
2. 해당 실행이 성공했는지 확인하고, 공개 사이트에서 변경된 자산·동작을 직접 확인한다. 필요하면 공개 파일과 대상 커밋의 내용을 비교한다. PC·모바일 등 확인한 환경과 확인하지 못한 범위를 구분한다.
3. 릴리스까지 수행하는 작업이라면, 확인이 끝난 배포 소스 커밋에 `vX.Y.Z` 태그를 만들고 GitHub Release에 변경 내용과 검증 링크를 남긴다. 기존 태그는 이동·재사용하지 않는다. 태그·Release 생성 권한이나 도구가 없으면 미생성 상태를 명시한다.
4. `CHANGELOG.md`의 해당 변경 묶음을 `X.Y.Z — YYYY-MM-DD` 구역으로 확정하고 새 `Unreleased` 구역을 연다. 날짜는 공개 확인한 한국 날짜, 배포 SHA·Pages 실행 링크는 검증한 값으로 적는다. 이후 검증 문서 커밋을 만들더라도 태그를 그 최신 커밋으로 옮기지 않는다. `VERSION`은 다음 앱·콘텐츠 변경이 시작되기 전까지 같은 값을 유지한다.

운영 문서만 병합되어 Pages가 다시 실행되는 경우에는 앱 버전을 올리거나 같은 번호의 태그를 다시 만들지 않는다. 릴리스 이후 문서 커밋이 추가될 수 있으므로 정확한 소스 구분에는 SHA도 함께 사용한다. 공개 버전은 마지막으로 확인한 배포·릴리스 기록으로 판단한다.

## 배포 실패와 되돌리기

- 실패 시 실행 링크, 대상 SHA, 오류와 공개 사이트 상태를 `verification.md`에 남긴다. GitHub 내부 배포 오류와 앱 코드·캐시 문제를 구분하고, 원인 근거 없이 캐시 번호나 무관한 코드를 바꿔 해결했다고 주장하지 않는다. 실패한 배포에 성공 태그를 붙이지 않는다.
- 코드 수정이 필요하면 새 수정 커밋을 만든다. 이미 공개한 변경을 되돌릴 때는 정상 동작했던 커밋을 기준으로 `git revert` 등 이력을 보존하는 방식으로 복구하고 새 PATCH 버전으로 기록한다. 롤백된 커밋·이유와 재배포 검증 결과를 남긴다.
- 공개에 실패한 미공개 변경 묶음은 같은 목표 버전으로 수정·재검증할 수 있다. 기존 정상 버전의 태그와 기록은 보존한다. 되돌릴 때도 학습 기록의 호환성과 저장 키를 확인한다.
