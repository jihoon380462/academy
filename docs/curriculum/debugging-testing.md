# 디버깅·테스트

| 항목 | 설계 |
| --- | --- |
| 과목 ID | `debugging-testing` |
| 범위 | 기초→실무 |
| 목표 | 문제를 재현하고 관찰 증거로 원인을 좁힌 뒤, 수정의 효과와 재발 방지를 검증한다. |
| 진입 지식 | `python` 또는 `c-family`의 함수·조건·반복·예외 기초. 파일·HTTP 관련 레슨은 그 기능을 사용하는 시점에만 해당 개념을 선행한다. |
| 완료 기준 | 작은 프로그램의 결함 하나에 대해 최소 재현, 원인 설명, 최소 수정, 실패를 드러내는 회귀 테스트, 검사 결과를 묶어 남긴다. |
| 콘텐츠 상태 | 설계만 완료, 본문 미작성 |

## 범위와 과목 경계

- 재현→관찰→가설→실험→수정→검증의 과정과 단위·통합 테스트의 설계를 중심으로 한다. 실무 상한은 작은 라이브러리·명령줄 도구·웹 기능의 일반적인 결함을 진단하고 자동 검사를 유지하는 수준이다.
- `python`·`c-family`의 문법 오류 설명을 활용하되 이 과목은 원인 추적과 검증 방법을 소유한다. 환경 운영은 `linux`, API 계약 자체는 `http-api-sdk`, 설계 변경은 `object-design`, CI 서비스 조작은 `github`에서 자세히 다룬다.
- 전문 보안 침투, 대규모 분산 장애 대응, 모든 언어의 디버거 옵션, 안전 필수 소프트웨어 인증 절차는 제외한다. 외부 기능을 재현할 때 실제 이용자 데이터나 유료 자원을 필수로 요구하지 않는다.
- 설계 제안: Python의 pdb·unittest와 pytest를 설명 예로 삼고 C++/C#의 같은 개념을 짧게 연결한다. 특정 프레임워크의 완주가 목표가 아니며 집필 시 공식 문서 버전을 확인한다.

## 후속 집필 주의

- 레슨마다 예제 5개, 챕터마다 복습 10개를 유지한다. 예제는 실패 메시지 해석·다음 관찰 선택·테스트 누락 찾기·작은 수정·검증 결과 해석을 섞는다.
- 검증할 제품 기능이 아닌 내부 구현 세부를 그대로 재현하는 테스트를 정답으로 강제하지 않는다. 테스트의 비용과 실제 결함 발견 능력을 함께 설명한다.
- 라이브 API나 실제 사용자의 파일을 호출하는 예제는 기본으로 삼지 않는다. 재현용 임시 자료와 명시적인 정리 경계를 사용한다.

## 참고한 공식 범위 자료

확인일: 2026-11-10 KST. 아래 자료로 개념 범위와 도구의 역할을 확인했으며, 챕터 구성과 레슨 목표는 이 사이트를 위한 독자적인 설계 제안이다.

- [pytest flaky tests](https://github.com/pytest-dev/pytest/blob/main/doc/en/explanation/flaky.rst) — 공유 상태·순서·시간 비교가 불안정한 테스트와 연결되는 사례를 확인했다.
