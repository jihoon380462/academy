# 개체지향·설계

| 항목 | 설계 |
| --- | --- |
| 과목 ID | `object-design` |
| 범위 | 기초→실무 |
| 목표 | 상태와 책임, 계약과 의존성을 나누어 변경에 대응하기 쉬운 작은 프로그램을 설계한다. |
| 진입 지식 | `python` 또는 `c-family`의 함수·자료형·컬렉션 기초. 클래스 문법은 첫 챕터에서 연결하므로 다른 언어 트랙 전체를 요구하지 않는다. |
| 완료 기준 | 작은 프로그램에서 새 요구사항 하나를 추가하며 책임 분리, 계약, 변경 범위와 테스트 방법을 설명하고 설계 결정을 짧게 기록한다. |
| 콘텐츠 상태 | 설계만 완료, 본문 미작성 |

## 범위와 과목 경계

- 표시명은 사용자 지정인 “개체지향·설계”를 유지한다. 본문에서는 일반적으로 쓰는 용어 “객체지향”을 소개하고 동일한 학습 분야임을 설명한다.
- 객체의 상태·행동·책임, 계약, 구성 방식, 모듈 경계와 작은 리팩터링을 깊게 다룬다. 실무 상한은 한 프로젝트 안의 모듈과 저장·입출력 경계를 관리하는 수준이다.
- 언어별 클래스·제네릭·수명 문법은 `python`·`python-practice`·`c-family`가, 실제 테스트 도구는 `debugging-testing`이 소유한다. 데이터베이스 스키마는 `sql`, HTTP 계약은 `http-api-sdk`로 연결한다.
- 마이크로서비스 전환, 엔터프라이즈 DDD 전체, 모든 디자인 패턴의 암기, 프레임워크 내부 구현, UML 표준 전체는 제외한다. 객체지향만이 모든 문제의 정답이라는 전제를 두지 않는다.
- 설계 제안: 작은 Python 또는 C# 예를 한 주 언어로 일관되게 쓰고 도식을 함께 제공한다. 언어 문법·라이브러리 버전은 구현 시 공식 문서를 확인한다.

## 후속 집필 주의

- 모든 레슨은 예제 5개, 챕터는 복습 10개로 구성한다. 객체 상태·호출 순서·변경 파급을 그림으로 보여 줄 수 있도록 목표를 유지한다.
- “SOLID” 등 약어는 의미를 설명한 후 연결한다. 원칙을 기계적으로 적용해 클래스·인터페이스 수를 늘리는 답을 정답으로 만들지 않는다.
- 동일한 문제의 단순 함수 버전과 객체 버전을 비교할 수 있지만 모든 언어의 문법을 동시에 나열하지 않는다.
